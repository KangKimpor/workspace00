# Pages and databases: first working phase

The web app keeps its existing React/Tiptap editor, Yjs documents, Dexie IndexedDB workspace and field-clock Supabase sync. Database items are pages with `type: "row"`, `databaseId` identifying the database page, and an optional `parentId`. A database page and its `DatabaseDefinition` share an ID. Ordinary pages retain their document and nesting behavior.

## Page lifecycle

- `movePage(id, parentId)` checks the selected account's authoritative records in one transaction. Destinations must exist and be active; self/descendant cycles are rejected, including cycles through database membership. Moving an ordinary page into a database converts it to a row. Existing rows can move between databases, and both `parentId` and `databaseId` change together. Existing imported database roots with a self-referencing `databaseId` remain readable and editable.
- `duplicatePage(id, title?)` atomically duplicates the active subtree, database definitions, documents and attachments. Page IDs, internal relation targets, attachment IDs, attachment covers and rich-text attachment references are rewritten. Encrypted attachments are authenticated with their original document keys, then re-encrypted with fresh keys/IVs bound to the new attachment IDs; cloned document nodes receive those keys/IVs. Plain attachments retain their bytes. Preparation runs outside the write transaction; the transaction revalidates the source account, subtree, documents and attachments before committing. Missing attachment keys, unsynced encrypted files or changed source data reject the copy rather than commit broken content. Arbitrary text stays unchanged. Root template status, favorites and archive status are cleared. Version history and calendar links stay associated with the source. Protected/encrypted subtrees must be unlocked before duplication, so a copy cannot silently omit protected content.
- `properties.__archived` stores an ISO timestamp or `null`. Archive is independent from `deletedAt`/Trash. Archived roots hide their descendants in ordinary navigation. `archivePage` and `unarchivePage` update one property clock, preserving concurrent edits to other properties. Restoring Trash preserves archive status.
- `listPages()` excludes Trash and Archive; `listPages(false, true)` includes Archive; existing `listPages(true)` includes both for backup and Trash compatibility. Both flags can be supplied explicitly.
- `properties.__template: true` marks a saved user template. Instantiating it duplicates its content and clears template status on the new root.
- `properties.__workspaceDatabase: true` distinguishes a generic database from legacy preset projects. Generic databases do not enter project inference or Today task selection.
- `patchPageProperties(id, patch)` stamps only supplied property keys. Editor text callbacks, template flags, row cells and completion actions use it to avoid replacing another action's properties with a stale UI snapshot. Explicit `null` clears a value. Invalid property values/prototype keys are rejected; protection state belongs to the encryption APIs, and locked pages reject searchable-text writes.

## Database metadata and APIs

`createDatabase(title, { properties, views, defaultProperties? }, pageExtras?)` commits the page and definition together. Invalid definitions roll back the page and sync queue. `createPage("row", ..., { databaseId, properties })` applies detached copies of database defaults; explicit row values override defaults. Defaults do not rewrite existing rows.

`PropertyType` includes `person`. Person values are display strings or arrays of display strings; this phase does not implement shared workspace membership. `DatabaseView.visibleProperties` optionally lists visible property IDs. Omitting it preserves the existing presentation defaults; an empty array intentionally hides optional properties.

Use `patchDatabaseView(databaseId, viewId, patch)` for view edits and `deleteDatabaseView(databaseId, viewId)` for deletion. New/recreated views require a complete name and type. A deleted view rejects stale partial forms. View names, filters, sorting, grouping and property visibility persist across reloads and sync.

Runtime validation runs before persisted or synchronized database definitions are accepted. It checks property/view identities, known kinds, options, filters and nesting limits, sorting directions, and references from views/defaults to schema properties. Local page moves validate account ownership, destination existence and cycles. Sync does not require referenced pages to arrive first, because entity changes may be delivered independently. IndexedDB account partitions and the existing authenticated Supabase sync boundary remain authoritative; a page ID does not grant access to another account.

## Transport and compatibility

No SQL migration is needed for these fields: existing generic entity JSON and field-clock storage carry them. Archive/templates/generic markers use the existing page properties map. The public definition still exposes `views: DatabaseView[]`; the store additionally writes independently stamped `views.<encodedViewId>.<attribute>` fields. IDs are URI encoded, including dots. A per-view `deleted` stamp is the tombstone. Decode collects attributes before applying the tombstone, making concurrent rename/delete delivery order irrelevant. Concurrent edits cannot revive a deleted view; explicit complete recreation can.

Legacy whole-array `views` values remain readable. Attribute stamps older than the legacy array's stamp do not override that array. A newer legacy client writing a whole array can therefore replace more recent individual settings from its stale snapshot. Upgraded clients should use the per-view APIs, and deployment should avoid prolonged mixed-version editing. `saveDatabase` remains compatible with complete schema writes, but concurrent stale whole-definition snapshots retain last-writer behavior. Property schema arrays and default maps are still one stamped field each; different view attributes merge independently, while simultaneous edits to the same attribute use the existing clock winner. Filters/sorts within one attribute do not merge individual clauses. Rich text continues using Yjs rather than metadata clocks.

The IndexedDB schema version and archive format remain unchanged. Existing backups load through the same validation and legacy view decoder. New backups export the public decoded definitions, including archive/template/default/visibility metadata; import regenerates field stamps. Rollout should retain backups and exercise an old-data load, export/import, two-device view edit and archive/restore smoke test. Existing protected document handling and server-side account isolation must remain enabled.

This phase does not add sharing, formulas, a timeline view, or collaborative person identities. Native desktop work remains paused.
